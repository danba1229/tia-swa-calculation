## 1. 횡단보도

공식 출처:
- 서울시 교통안전시설물 횡단보도 정보: https://data.seoul.go.kr/dataList/OA-15554/S/1/datasetView.do
- 서울시 교차로 및 횡단보도 시설·위치정보: https://data.seoul.go.kr/dataList/OA-23081/F/1/datasetView.do

기존 확보 SHP는 2021년 ZIP의 횡단보도 37,324 POLYGON, EPSG:5186이다. 현재 API 표본에는 X/Y와 공란이 함께 존재하고 geometry 필드도 공란이었다. 따라서 API 원본 전체를 무조건 지도에 올리면 안 된다. SHP와 API는 서로 다른 스냅샷이며 시점을 구분한다.

2026-08-24 파일명의 최신 보완 XLSX를 다시 읽었다. 21,776행, 횡단보도 관리번호 21,776개, 자치구·교차로관리번호·횡단보도종류·보행등유무·교차로명·X/Y가 있다. 보행등유무는 유 13,523행, 무 8,253행이다. 같은 교차로번호 안에도 유·무가 함께 존재한다. 예를 들어 교차로번호 1756의 표본 두 횡단보도는 각각 유와 무였다.

**보행등유무는 개별 횡단보도의 속성이지 차량 교차로 전체의 신호 운영 여부가 아니다. 보행등 ‘무’를 비신호교차로로 변환해서는 안 된다.** 이 XLSX의 X/Y 좌표계는 아직 원본 근거로 확정하지 못했다.

구현 필드: 횡단보도 관리번호, 종류, 교차로명/번호, 보행등유무, 위치, 사업지 거리, 자료 버전. 범위와 교차하는 폴리곤을 검색하고, 점 자료일 때는 점 자료임을 표시한다.

## 2. 험프

공식 출처: https://data.seoul.go.kr/dataList/OA-15541/S/1/datasetView.do

이번에는 공식 `교통안전시설물 테이블 정의서(험프).pdf`를 직접 내려받아 코드표를 읽었다. `A067_KND_CDE`의 공식 값은 다음과 같다. SHP는 필드 길이 제한으로 `A067_KND_C`를 사용한다.

| 코드 | 공식 코드명 | 기존 확보 2025-04-17 SHP의 실제 행 수 |
|---|---|---:|
| 001 | 요철 | 7,023 |
| 002 | 이미지 | 11,361 |
| 합계 | 두 유형 합계 | 18,384 |

이 숫자는 해당 파일의 객체 수이며 현재 서울 전체 운영 시설 수가 아니다. 이미지를 실제 돌출 시설과 섞어 ‘과속방지턱 18,384개’로 표시하면 오해를 만든다. 처음부터 유형별로 분리하고 공식 용어를 그대로 쓴다. 높이·길이·고원식 횡단보도 여부 등 원본에 없는 속성을 추정하지 않는다.

공식 SHP는 POLYGON, EPSG:5186이고 원본 geometry로 공간검색할 수 있다. API sample은 `SPC_DATA`가 공란이고 X/Y 열이 없어 현재 위치 자동화에는 SHP가 더 명확한 출발점이다. 자료 시점과 품질 검증을 통과한 버전만 사용한다.

## 3. 신호교차로

공식 출처:
- 교차로: https://data.seoul.go.kr/dataList/OA-15534/S/1/datasetView.do
- 교통신호제어기: https://data.seoul.go.kr/dataList/OA-15538/S/1/datasetView.do

이번에 `A008_P_20250814.zip`, 교차로 정의서, 제어기 정의서와 2021년 제어기 ZIP을 실제 다운로드하고 API sample도 확인했다.

2025-08-14 교차로 SHP는 8,097 POINT, EPSG:5186이다. 교차로 유형코드의 실제 구성:

| 코드 | 공식 의미 | 원본 행 수 |
|---|---|---:|
| 001 | 단일로 | 4,534 |
| 002 | 3거리 | 1,744 |
| 003 | 4거리 | 1,797 |
| 004 | 5거리 | 21 |
| 005 | 6거리 | 1 |

따라서 8,097행 전체를 교차로 수로 집계하면 잘못된다. 단일로를 제외하면 이 파일의 3~6거리 원본 레코드는 3,563개다. 이 또한 현재 서울 전체 교차로 완전 목록이라는 뜻은 아니다. API 서버 보고 total 8,638과 파일 8,097이 달라 시점·표출상태 등을 검증해야 한다.

교차로 표의 `CSS_NUM`(API `INTR_CD`)과 제어기의 `CSS_NUM`(API `INTR_NO`)는 공식 정의서에서 교차로번호로 설명한다. 관리번호 `MGRNU`와 혼동하지 않고 이 번호로 연결할 수 있다. 실제 과거 제어기 파일과의 연결도 일부 확인했지만, 2021년 제어기와 2025년 교차로 자료의 조합이므로 현재 상태 확정에는 쓰지 않는다.

제어기 정의서의 중요한 코드:
- 형태 `001~006`: 2~7현시.
- 형태 `008`: 단순보행.
- 형태 `009`: 점멸.
- 시스템 `005`: 경보.
- 시스템 `011`: 철거.

**제어기가 있다고 모두 일반 차량 신호교차로로 분류할 수 없다.** 교차로 유형, 제어기 용도·운영형태·철거 상태, 연동교차로 연결, 자료 시점, 연결 누락·중복을 확인한 뒤 ‘자료상 신호교차로’로 분류한다. 단순보행·점멸은 별도 검토 상태를 남긴다. 표출구분과 작업구분은 실제 현장 운영상태와 동일하다고 가정하지 않는다.

권장 구현: 교차로 전체 기본 목록을 먼저 만들고 신호 분류 근거, 연결된 제어기번호, 제어기 형태, 자료 버전, 수동 판정 이력을 함께 저장한다. 이름이나 신호등과의 단순 거리만으로 자동 확정하지 않는다.

## 4. 비신호교차로

이번 확인한 교차로 파일/API/정의서에는 신호·비신호를 직접 확정하는 열이 없다. 교차로번호가 없는 제어기, 과거 자료, 단순보행·점멸 및 중복 연결이 있으므로 다음 추론은 금지한다.

- 제어기 목록에 없으니 비신호.
- 근처에 신호등 점이 없으니 비신호.
- 횡단보도 보행등이 ‘무’이니 비신호.
- 도로선이 교차하니 차량 교차로(입체교차·진출입구·도로망 분절일 수 있음).

완전 자동 확정에는 지자체/경찰 등 관리기관의 교차로별 운영형태가 명시된 공식 자료가 필요하다. 필요한 필드는 교차로 ID·명칭·좌표, 신호/비신호/점멸 등 운영구분, 교차로 형태, 관리기관, 기준일, 운영 변경 이력이다. 이번에 그러한 최신 공개 원본을 확보했다는 근거는 없다. 기관 제공신청을 실제 전송하지 않았다.

현실적인 앱 구성은 `신호 확인 / 비신호 확인 / 수동확인필요`로 관리하는 것이다. 공식 자료 또는 현장 확인으로 비신호가 확인된 항목만 비신호 목록·집계에 포함한다. 공식 도로망으로 후보를 만들 수는 있지만 확인된 비신호교차로 수와 분리한다.

## 5. 보도육교

공식 출처:
- 서울시 육교 공간정보: https://data.seoul.go.kr/dataList/OA-21210/S/1/datasetView.do
- 서울시 육교정보: https://data.seoul.go.kr/dataList/OA-22361/F/1/datasetView.do
- 서울시 보도육교 위치현황: https://data.seoul.go.kr/dataList/OA-22353/F/1/datasetView.do

공간 API `tbTraficBrdge`의 sample 5행이 성공했다. `NODE_WKT`의 POINT, `LNKG_WKT`의 LINESTRING, 시작·종료 노드 ID, 링크 길이와 행정구역이 있다. 공식 페이지는 WGS84이며 **‘20년 기준’**이라고 설명한다. 페이지 갱신일은 2026-10-08로 나오지만 이를 시설 기준일로 바꾸지 않는다.

API 서버 보고 total은 2,967이나 이것은 노드/링크 레코드 수이지 육교 2,967개가 아니다. 표본에는 시설명이나 육교별 단일 관리 ID가 없어 노드·링크의 시설 단위 묶음과 명칭 연결을 검증해야 한다.

별도 CSV를 실제 다운로드했다.
- `서울특별시_육교정보_20221231.csv`: 149행. 육교명, 도로명, 주소, 연장, 통행제한높이, 폭, 장애인 편의시설 여부/종류, 관리기관, 기준일(표본 2022-12-31). 위경도 열은 없다.
- `서울특별시_보도육교 위치현황_20211220.csv`: 152행. 관리기관, 명칭, 위치, 노선명. 위경도 열은 없다.

구현은 공간 API를 위치 레이어로 사용하고 명칭/주소 대장을 보완하는 방식이 가능하다. 서로 다른 연도의 파일을 단순 합산하거나, 가까운 객체라는 이유만으로 동일 육교로 확정하지 않는다. 불확실한 매칭은 수동확인필요로 남긴다. 주소 지오코딩을 사용할 경우 공식 측량 위치와 구별하고 실제 도로 횡단 위치를 확인한다. 특히 철거·이전·새 육교는 최신 대장이나 현장 확인이 필요하다.

## 경기 및 적용 범위

경기데이터드림 공식 통합검색에 육교·교차로·비신호·과속방지턱을 각각 요청했으나 모두 503으로 응답했다. 따라서 서울의 확인 결과를 경기 31개 시군에 그대로 적용한다고 주장할 수 없다. 시군별 좌표·유형·운영구분·기준일을 포함한 원본을 검증한 뒤 해당 지역을 활성화해야 한다.

## 추천 STEP 10 구성

- 탭: 횡단보도 / 험프 / 신호교차로 / 비신호교차로 / 육교.
- 험프 필터: 공식 코드 ‘요철’과 ‘이미지’를 별도로 표시·집계.
- 교차로 공통 기본 목록에서 신호 분류 근거를 관리. 분류 미확인 항목은 별도 확인 목록으로 노출하며 두 확정 탭의 건수에 포함하지 않음.
- 원본 버전·행별 기준일·마지막 확인 시각을 구분. 과거자료를 최신 현황으로 표시하지 않음.
- 조회는 상단 주소·직사각형 범위와 연동하고, 선·면 시설은 조사 범위와의 교차로 검색. 표·CSV·지도 간에 같은 원본 ID와 분류 기준을 사용.
- 누락 셀은 `수동확인필요`, 원인은 표 제목 옆 설명에 표시. API 오류·미지원 지역과 정상 조회 0건을 구별.

API sample은 5행 검증이며 전체 API 데이터의 수록범위·품질 검증 완료를 뜻하지 않는다. 오늘 확보한 실제 응답, 공식 PDF와 텍스트, SHP/CSV 원본, `intersection-controller-profile.json`을 같은 폴더에 보관했다.
